# Рефакторинг структуры и legacy

Читай, когда нужно **перенести** код, разрезать god-module, выровнять кусок legacy или убрать нарушение границы. Не используй этот файл как повод мигрировать весь репозиторий на FSD или другой шаблон.

Новое размещение — по треку зоны ([architecture-tracks.md](architecture-tracks.md)) и discovery ([principles-and-discovery.md](principles-and-discovery.md)). Контракт импортов — [boundaries-and-imports.md](boundaries-and-imports.md). Вёрстку при переносе UI не переписывай «заодно» — это другой скил.

Логирование при переносе **не** добавляй, если репо/задача этого не требуют.

## 1. Цель и ограничение зоны

Зафиксируй до правок:

- что является **публичным контрактом** сейчас (экспорты `index`, `package.json` `exports`, пути потребителей, URL API, пропсы);
- какие потребители его импортируют (поиск по репо, не по памяти);
- какой стиль **зоны** целевой (как соседи), не идеал учебника.

Двигаешь только затронутый модуль и его прямых потребителей. Соседние god-module, «раз уж открыл», не трогай.

Пользователь не просил миграцию — не заводи новые слои/фиче-папки под остальной `src`. Не превращай layered в domain (и наоборот) в том же переносе.

## 2. Безопасная последовательность

Иди по шагам. Не удаляй старый путь в том же diff, где ещё живы потребители.

1. **Сохрани контракт.** Список экспортов и семантику хуков/компонентов не меняй в том же шаге, что и переезд (кроме явной задачи сломать API).
2. **Создай новое место** по аналогу зоны: папка, public API, сегменты как у соседа того же типа.
3. **Перенеси внутренности** (ui/api/model) на новое место. Поведение и имена снаружи те же.
4. **Старый путь сделай фасадом:** реэкспорт из нового API или тонкая обёртка. Потребители пока продолжают собирать.
5. **Переведи потребителей** зоны на новый public API (без deep import в старую внутренность).
6. **Удали** пустую оболочку и мёртвые файлы, когда поиск больше не находит старый путь.
7. **Проверь** уже существующими командами репо по затронутой области. Watch-режим не запускай. Архитектурный линтер — одноразово, если он есть (`steiger` без `--watch`, boundaries, Nx). Не вызывай скрипт, который сам уходит в watch.

Если перенос большой — остановись после шага 4 (фасад) и не ломай потребителей в том же заходе, пока задача не требует полного выпила.

```
# шаг 4 — старый фасад, иллюстрация
// old-module/index.ts
export { ThingForm, useCreateThing } from '@/new-place/thing';
```

Не копируй этот alias в репо, где других alias нет: реэкспорт относительным путём, как принято здесь.

## 3. Публичные контракты

Пока жив старый импорт — его нужно либо сохранить, либо заменить **всех** потребителей в зоне задачи.

- Переименовал экспорт — обнови всех импортёров в том же изменении зоны, не оставляй мёртвое имя «на потом» без реэкспорта.
- Типы, которые торчали наружу, переезжают вместе с фасадом; не заставляй потребителей импортировать `model/types` вглубь.
- Маршруты, store registration, data-fetching inject (`injectEndpoints`, route config) подключи в **том же месте**, где в репо подключают аналоги — не в случайный файл и не «потом».
- Моки, stories, тесты рядом с модулем — перенеси вместе, если они колоцированы; отдельные тестовые задачи не выдумывай, если план без тестов.

Сломал контракт без нужды — это баг переноса, не «очистка».

## 4. Legacy и смешанная структура

Смешанный репозиторий — норма. Новый код в зоне пишется в стиле **этой** зоны (шаг 2 `SKILL.md`), а не в стиле желаемого конечного состояния всего продукта.

- Strangler: новый модуль рядом → потребители постепенно через фасад → старая папка пустеет. Не big-bang `git mv src src-old`.
- Файл в «неправильной» папке, но задача — баг/поле формы: **не** переезжай, если граница не в скоупе.
- Два стиля в одной зоне — спроси, куда переносить; не угадывай и не плоди третий.
- Framework-owned `app/` / `routes/` не «выравнивай» под FSD-`app/` переносом роутов фреймворка.

Не создавай параллельный мир (`src/fsd-entities/` рядом с `src/components/`) «для новых фич».

## 5. God-module и чрезмерное дробление

Резать god-module — по границам сценария/сущности, которые уже видны в коде (отдельный API, отдельный экран, отдельная ответственность), не по числу файлов.

После нарезки каждый кусок должен иметь смысл и public API. Если два новых слайса сразу импортируют друг друга — рано резал: верни вместе или вынеси общий контракт вниз, см. циклы в [boundaries-and-imports.md](boundaries-and-imports.md).

Не дроби «один компонент — один слайс», если аналог зоны живёт крупнее. Не склеивай несвязанные сценарии в shared, «чтобы меньше папок».

## 6. Стоп-условия

Остановись и спроси / сузь скоуп, если:

- перенос требует нового архитектурного стиля на весь `src`;
- нужно включить выключенное правило enforcement или добавить steiger/Nx;
- публичный контракт сломается у модулей вне задачи;
- неясно, framework-owned каталог это или слой продукта.

Иначе: минимальный перенос, фасад, потребители зоны, существующие проверки, без миграции репозитория.
