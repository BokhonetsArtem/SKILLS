# Границы, public API и импорты

Читай, когда решаешь, **что экспортировать наружу**, откуда импортировать, как не создать цикл и чем разрешён кросс-модульный контракт. Слой/модуль уже выбран в [architecture-tracks.md](architecture-tracks.md) — этот файл не выбирает трек заново.

Правила ниже подчиняются репозиторию: если соседи и enforcement говорят иначе — повтори репо, не учебник. Пути `@/entities/skill`, `@x`, `@/shared/config` не копируй в проект, где их нет.

## 1. Public API

Public API — **ограниченный набор явно поддерживаемых** внешних точек модуля/слайса/пакета: то, что уже импортируют потребители или что описано как вход (`index`, `exports`, разрешённый subpath). Неописанный путь во внутреннюю папку — не API, даже если бандлер его собирает.

Типичные формы (бери ту, что в репо; их может быть **несколько**, если так задано):

- корневой `index.ts` / `index.tsx` слайса или фичи;
- `package.json` `exports` (включая несколько разрешённых subpath);
- явный `public.ts` / `mod.ts`, если так у соседей.

Наружу — только то, чем реально пользуются снаружи: компоненты сценария, хуки query/mutation, типы контракта. Внутренние хелперы, схему валидации, куски UI без автономного смысла — не экспортируй «на будущее».

```
slice-or-feature/
  index.ts              ← наружу
  ui/Form.tsx           ← внутрь
  api/client.ts         ← внутрь
```

Потребитель:

```ts
// надо — как у соседей зоны (alias или относительный index)
import { ThingCard, useGetThingQuery } from '@/entities/thing';

// не надо — deep import мимо API
import { ThingCard } from '@/entities/thing/ui/ThingCard/ThingCard';
```

В репо без barrel — импорт публичного файла, который **уже** считается фасадом (например `ThingCard.tsx` в корне фичи). Не заводи `index.ts` во всём дереве, если соседи без баррелей.

Реэкспорт через public API не должен тянуть тяжёлые внутренности ради одного типа: при необходимости тип живёт в контрактном файле, который API и так экспортирует.

## 2. Deep imports

Deep import — путь **мимо** public API во внутреннюю папку (`ui/`, `model/`, `lib/`, `internal/`).

Не делай так в новом коде, если:

- enforcement это запрещает (`steiger` `no-public-api-sidestep`, `eslint-plugin-boundaries`, Nx tags);
- либо аналоги зоны импортируют только фасад.

Исключения — только уже принятые в репо:

- файлы того же слайса/модуля между собой;
- явный канал кросс-импорта (ниже);
- существующие оверрайды линтера на конкретные глобы (например app-слой). Не расширяй оверрайд на новую папку без запроса.

Нашёл deep import в зоне и задача — исправить нарушение: выведи нужное в public API (или в принятый кросс-канал) и переведи потребителя на фасад. Не размазывай новые deep import «как уже было в легаси», если цель задачи — граница.

## 3. Направление зависимостей

Следуй треку зоны, не графу «кто удобнее импортирует».

| Трек | Направление |
| --- | --- |
| FSD | Только вниз по слоям: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Слайсы одного слоя друг друга не импортируют (кроме принятого кросс-канала сущностей) |
| Feature / module | Фича → shared/lib/ui. Фича ↛ внутренности другой фичи. Страницы/app собирают фичи |
| Layered | Экран → components/hooks → services/api/store. `utils` не знает страницы и компоненты |
| Domain | К домену: UI → application → domain; infrastructure реализует порты домена, если порты уже есть. Домен не знает HTTP и роутер |

Запрещено в новом коде: нижний слой/модуль импортирует верхний; домен тянет роутер или страницу; `shared` тянет фичу или сущность.

Проверяй **реальные** import-строки и alias, не только относительные `../`. Циклический `import type` всё ещё цикл для bundler/eslint, если инструмент так считает — не спорь с ним в этом скиле.

## 4. Циклы

Симптом: два модуля импортируют друг друга (напрямую или через третий), runtime `undefined`, линтер `import/no-cycle`, steiger, Webpack/Vite cycle warning.

Как рвать — минимальным движением, без «нового стиля»:

1. Вынести **общий контракт** (тип, константа, узкий UI без сценария) в уже существующий нижний слой / `shared` / kernel домена — туда, куда в репо кладут такое.
2. Инвертировать зависимость: колбэк, проп, инъекция, событие — владелец сценария вызывает соседа через его public API, а не наоборот.
3. На FSD между сущностями — только если в репо уже есть канал вроде `@x`: сущность A не импортирует `@/entities/B` целиком, а узкий контракт B для A.
4. Не «решать» цикл deep import-ом в третий модуль и не отключать правило цикла глобально.

Новый код не должен замыкать граф. Легаси-цикл вне зоны не развязывай заодно — [refactoring.md](refactoring.md).

## 5. Кросс-модульные контракты

Когда двум модулям одного уровня реально нужно пересечься:

| Если в репо уже есть | Делай так |
| --- | --- |
| FSD `@x/<consumer>` (или аналог) | Узкий экспорт **для конкретного** потребителя, не второй полный `index` |
| Фасад / `public` соседнего модуля | Импорт фасада, не внутренностей |
| Shared-контракт (типы API, DTO, кит) | Только безжизненный контракт, не сценарий фичи |
| Nx tags / boundaries elements | Импорт разрешённых тегов, не обход через относительный путь |

Не изобретай `@x`, публичные баррели и «anti-corruption» пакеты в репозитории, где их нет. Нет канала — сначала общий кусок вниз по направлению зависимостей; если некуда без нарушения трека — спроси.

## 6. Escape hatches

Допустимы **только** как уже существующая практика репо, не как новый приём скила:

- оверрайд enforcement на уже перечисленные глобы (не включай выключенные правила и не расширяй scope);
- временный реэкспорт со старого public API при переносе — [refactoring.md](refactoring.md);
- composition root (`app`, роутер, store setup) собирает модули — это не обход, а его работа;
- framework-owned `app/` / `routes/` импортирует продукт как принято у фреймворка.

Не escape hatch: `// eslint-disable` на boundaries «чтобы собрать», произвольный deep import, второй alias на internal, отключение `steiger` / Nx для папки новой фичи.

Нет архитектурного линтера — всё равно держи направление и фасады как у аналога. Не добавляй `steiger` / `eslint-plugin-boundaries` / Nx boundaries этим скилом.
