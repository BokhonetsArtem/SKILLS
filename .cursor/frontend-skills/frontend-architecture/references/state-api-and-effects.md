# State, API и эффекты

Читай, когда нужно решить, **кто владеет** состоянием, куда класть query/mutation, клиент API и побочные эффекты. Библиотеку бери из репозитория. Не подставляй Redux, RTK Query, Zustand, TanStack Query, Pinia, MobX или второй клиент «для удобства», если его нет в проекте / в зоне уже другой.

Трек (FSD / feature-module / layered / domain) уже выбран — этот файл не меняет слои, только владельца данных внутри них. Слои — [architecture-tracks.md](architecture-tracks.md). Фасады — [boundaries-and-imports.md](boundaries-and-imports.md).

Логирование в state/API **не** добавляй, если план/репо этого не требуют.

## 1. Какой это state

Сначала классифицируй, потом ищи аналог того же типа в зоне.

| Вид | Что это | Где обычно живёт |
| --- | --- | --- |
| Server / удалённый кэш | Ответ API, список, карточка, теги инвалидации | Слой data-fetching репо (query-клиент, slice API, сервис), не в случайном компоненте |
| Client / UI | открыт ли drawer, активный таб, hover | Локально в компоненте или в узком store модуля, который это показывает |
| Form | значения полей, ошибки валидации, dirty | Форма / feature-сценарий submit; не глобальный store «на всякий случай» |
| URL / query params | фильтры, страница, id в маршруте | Как у соседних экранов: роутер, search params, связка с запросом |
| Session / auth | текущий пользователь, токен-обвязка | Уже существующий auth/session модуль репо, не новая копия в фиче |

Не складывай всё в один глобальный store. Не дублируй server state в Redux/Zustand «чтобы было под рукой», если в репо уже query-кэш.

Владелец — модуль, у которого есть **причина писать** или **канон читать**. Два писателя одного поля без контракта — ошибка размещения.

## 2. API: клиент, query, mutation

Базовый HTTP/клиент (axios instance, `baseApi`, `fetcher`) — там, где он уже лежит (часто shared/lib/platform). Новый экземпляр клиента не заводи, если есть один.

Эндпоинты и хуки клади **как аналог того же типа** в зоне, не как «правильный FSD из статьи».

Универсальные эвристики (отменяй, если соседи иначе):

- **Чтение справочника / сущности** (список, by id, теги кэша) — рядом с владельцем сущности или ресурса.
- **Сценарий изменения** (создать, удалить, submit формы) — рядом с фичей/use-case, который это делает, не в UI-ките.
- Инвалидация кэша и optimistic update — у мутации-сценария, если аналоги так делают; не размазывай `onQueryStarted` / `invalidateQueries` по shared-кнопке.

```
# иллюстрация, не канон чужого репо
entities/thing/api/     → query чтения
features/thing/create/  → mutation создания + форма
shared/api/             → base client, если он уже там
```

На треке **feature/module** query и mutation часто живут **внутри одной фичи** — не вынимай «entity API» в несуществующий слой entities.

На треке **layered** запросы — `services`/`api`/`hooks`, как у соседа; не выноси их в `domain/application`.

На треке **domain** запросы — data/infrastructure; сценарий — application; UI только вызывает use-case/хук фасада.

Не клади вызов сети в shared UI-примитив (кнопка «удалить» с захардкоженным URL). Примитив получает колбэк или хук сценария снаружи.

## 3. Выбор владельца по треку

Читай только абзац своего трека.

**FSD.** Entity держит модель и чтение сущности. Feature держит действие пользователя и связанные mutation. Widget/page композируют хуки, не объявляют новые эндпоинты, если в репо эндпоинты уже в entity/feature. Page может вызывать entity query, если так делают соседние страницы — не запрещай это «по чистоте». Shared — base client и инфра, не `createThing`.

**Feature / module.** Всё, что нужно сценарию (форма, хук, API фичи), — в фиче. Общий клиент и сессия — в shared/auth, как у соседей. Не выноси mutation в `src/api/` только потому что «все эндпоинты в одном файле», если фичи уже колоцируют API.

**Layered.** Список и мутации — в `services`/`hooks`, как у соседа. UI-флаг — в компоненте. Не заводи `application/` и не тащи весь server state в один god-store.

**Domain.** Домен не знает HTTP. Application оркестрирует. UI подписывается на хук/store фасада модуля. Не тащи RTK-слайс в глобальные `components/`, если store живёт в data/application.

Смешанная зона — копируй **экран того же типа** (таблица, форма создания), не «самый правильный» модуль из другого конца репо.

## 4. Побочные эффекты

Эффект (toast, навигация после submit, analytics, запись в storage, инвалидация) принадлежит **сценарию**, который его вызвал — feature / use-case / page-handler, как у аналога.

- Не прячь навигацию и refetch внутрь shared-кнопки или entity-карточки, если карточка в репо тупая.
- Не дублируй один эффект в UI и в API-обвязке без образца.
- Глобальные listeners (keydown, websocket) — в существующем app/provider/module, не в случайном виджете, если в репо уже есть точка подписки.

Локальность: эффект, нужный одному экрану, не поднимай в app-провайдер. Эффект, нужный всем сессиям, не оставляй в одной фиче, если аналог уже в app/auth.

## 5. Чего не делать

- Не добавляй второй state manager / query-клиент к уже существующему.
- Не переноси server state в form state и обратно без причины (не копируй весь GET в `useState` «для формы», если форма умеет инициализироваться из query, как соседи).
- Не делай god-store на весь продукт и не дроби store на файл-на-поле.
- Не клади доменные теги кэша и DTO в shared UI.
- Не выдумывай разделение «query в entity / mutation в feature» в репозитории без FSD или без такого аналога.

Неясно — открой ближайший create/list/filter той же зоны и повтори владельца 1:1. Всё ещё спорно — спроси, не внедряй новую библиотеку.
