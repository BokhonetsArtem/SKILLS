# Типы и валидация

Читай, когда нужны schema, типы значений, sync/async проверки или ошибки с сервера на конкретное поле. Стек уже выбран ([discovery-and-stack.md](discovery-and-stack.md)). Сниппеты — только examples своего трека.

Client validation — UX и ранняя обратная связь. Она **не** защита сервера: API всё равно валидирует и авторизует. Не пиши в коде и в комментариях, что «схема на клиенте достаточно».

## 1. Три контура: schema ↔ form values ↔ API DTO

Не склеивай их в один тип «на всякий случай».

| Контур | Что это | Типичные отличия |
| --- | --- | --- |
| Form values | То, чем владеет форма | пустая строка vs `undefined`, `File` / base64 vs URL, id-массив вместо объектов |
| Schema | Правила для form values | required, shape, refine/test; сообщения |
| API DTO | Тело запроса/ответа | другие имена, `null`, серверные id, без preview-only полей |

На submit маппируй form values → DTO так, как уже делают соседи зоны. На edit гидрацию — DTO/сущность → form values ([lifecycle-and-submit.md](lifecycle-and-submit.md)). Не пихай сущность API целиком в `defaultValues`, если форма ждёт другой shape.

Тип form values бери так, как в зоне: отдельный `FooFormValues`, `yup.InferType`, `z.infer` — не выдумывай третий стиль рядом.

Не дублируй схему ручными `if (!value)` в `onSubmit`, если resolver/`validationSchema`/`validate` уже это закрывает. Точечная проверка в submit допустима только для того, чего схема честно не выражает (редкий кросс-запрос). Не копируй одни и те же required в schema **и** в обработчик.

## 2. Sync и async validation

Режим (`onTouched` / `onChange` / `onSubmit`) — как у ближайшей формы зоны, не абстрактный «лучший режим».

| Задача | Куда класть |
| --- | --- |
| Формат, required, min/max, совпадение полей | Schema / `validate` трека |
| Уникальность на сервере до submit | Async schema test / `validate` с запросом **уже принятым** клиентом зоны; не новый HTTP-стек |
| Ошибка после мутации на поле | API трека (§3), не повтор всей схемы |

Async-проверка не должна блокировать ввод на каждый кейпресс, если соседи так не делают. Для проверки по вводу переиспользуй локальный debounce/cancellation-механизм: устаревший response не должен перезаписать ошибку для нового значения. При `AbortController` отмена — ожидаемый исход, не form error. Не добавляй новый data-fetching слой только ради validation. Не логируй значения полей.

## 3. Field-level server errors

Ошибка конкретного поля («email занят», «slug уже есть») должна оказаться **на поле**, а не только в toast.

| Трек | Куда писать |
| --- | --- |
| RHF | `setError('field', { type: 'server', message })`; сброс — успешный ввод / `clearErrors` / новый submit |
| Formik | `setFieldError` и/или `setStatus` + отображение `errors` / `status`; не подменяй это одним `setStatus` без поля, если ошибка привязана к полю |
| native | тот же словарь ошибок, что и для client validation; ключ поля совпадает с контролом |
| Другая library / framework-managed | field-error API уже выбранного трека или его локальный error map; не подставляй `setError`/`setFieldError` из чужой библиотеки |

Toast/alert — для общей неудачи запроса (сеть, 500, «не сохранилось»). Не вместо `setError` / `setFieldError`.

Разбор тела 400/409 — по контракту API зоны (массив `{ field, message }`, map, `message` на известное поле). Неизвестное поле — общая ошибка формы, не молчаливый toast-only.

Если соседние мутации показывают только общий toast, не считай это достаточным прецедентом для ответа API, который явно указывает поле: field-level ответ веди через API выбранного трека.

## 4. i18n текстов ошибок

| В репо | Что делать |
| --- | --- |
| Уже есть i18n (`react-i18next`, next-intl, vue-i18n, …) | Сообщения schema и server-field errors — через него. Ключи и namespace как у соседних schema, не новые «красивые» строки в JSX |
| i18n нет | Обычные строки как у соседей. **Не** внедряй i18n «заодно» с формой |

Не клади сырой ответ 500 в сообщение поля. Не логируй пароли, токены и PII из ошибок.

## 5. Что не делать

- Считать, что валидная клиентская схема = можно не проверять ответ API.
- Ставить Zod «потому что TypeScript», если зона на yup (и наоборот).
- Показывать только toast, когда бэкенд вернул ошибку поля.
- Копировать toast-only обработку как стиль, когда API вернул ошибку конкретного поля.
- Дублировать всю форму в `useState` «чтобы проще валидировать» рядом с RHF/Formik.
