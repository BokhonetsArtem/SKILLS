# Принципы и обнаружение архитектуры

Читай, когда подход репозитория **неясен**, зона **смешанная**, или нужно решить, выделять ли новый модуль. Конкретные правила слоёв — только в выбранном разделе [architecture-tracks.md](architecture-tracks.md). Не объявляй FSD, feature-folders, layered или domain «правильными по умолчанию».

Пути вроде `@/entities/skill` или слой `processes/` **не** переноси в чужой репозиторий. Сначала дерево и импорты **этого** репо.

## 1. Не классифицируй только по имени папки

Имя `app/`, `pages/`, `features/` само по себе ничего не доказывает. Смотри **вместе**: дерево, реальные импорты, alias, манифест, enforcement.

| Что видно | Это ещё не значит |
| --- | --- |
| Папка `app/` | Слой FSD. У Next.js App Router, Nuxt 3, Remix это часто **каркас фреймворка** |
| Папка `pages/` | FSD-слой pages. У Next.js Pages Router / Nuxt это маршруты фреймворка |
| Папка `features/` | FSD. Часто это просто feature-folders без слоёв entities/widgets/shared |
| Папка `shared/` или `common/` | FSD. Техническая свалка тоже так называется |
| README «мы на FSD» | Что код и линтер это соблюдают |

Каркас фреймворка и архитектурный слой могут **сосуществовать** (например Next `app/` + `src/entities`). Не сливай их в один «слой app» и не перекладывай маршруты фреймворка в FSD-`app/` без аналога в репо.

### Framework-owned каталоги

Это маршрутизация и composition root **фреймворка**, не доказательство FSD:

| Фреймворк | Типичный каталог | Как обращаться |
| --- | --- | --- |
| Next.js App Router | `app/` (часто в корне, иногда `src/app`) | Клади маршруты, `layout`, `page`, `loading` как у соседей фреймворка. Не называй это слоем FSD только из-за имени |
| Next.js Pages Router | `pages/` | То же: файловый роутинг фреймворка |
| Remix | `app/routes/` или `routes/` | Роуты Remix, не FSD-pages |
| Nuxt | `app/`, `pages/`, `layouts/` | Конвенции Nuxt |
| SvelteKit | `src/routes/` | Файловый роутинг SvelteKit |

FSD-слой `app/` — composition root **продукта**: провайдеры, роутер приложения, глобальные стили входа. Он есть только если в репо уже есть остальные FSD-слои и/или FSD-enforcement, а не потому что фреймворк назвал папку `app`.

Не уверен, framework-owned это или архитектурный слой — смотри содержимое и импорты, не ярлык. Спорно — спроси.

## 2. Сигналы: что смотреть в репо

Достаточно сигналов по **зоне изменения**, не полный аудит.

1. **Дерево** `src/` (или аналога): какие папки первого уровня реально живые, не заготовки.
2. **Соседи той же зоны**: куда уже кладут похожий экран / форму / API.
3. **Alias / config:** `tsconfig`/`jsconfig` `paths`, Vite/Webpack alias — какие слои или домены вообще предусмотрены.
4. **Манифест:** `package.json`, lockfile — `@feature-sliced/*`, state/data-fetching библиотеки.
5. **Enforcement** (если файл или зависимость есть):
   - `steiger` / `steiger.config.*` / `@feature-sliced/steiger-plugin`
   - `@feature-sliced/eslint-config` и родственные пакеты `@feature-sliced/*`
   - `eslint-plugin-boundaries` (+ settings boundaries в eslint-конфиге)
   - Nx: `@nx/enforce-module-boundaries` / `enforce-module-boundaries` в `nx.json` или eslint
6. **Реальные импорты** в зоне, не README и не «как принято в FSD».

Enforcement сильнее папки: если `steiger` или boundaries уже режут граф — следуй конфигу репо, даже если имена слоёв неидеальны. Не добавляй и не ужесточай enforcement в этом скиле.

Нет ни слоёв, ни фиче-папок, ни доменных модулей — это **неясный** проект: спроси стиль для нового места, клади как ближайшие соседи выбранной зоны.

### Когда это FSD (не только enforcement)

Имена папок сами по себе **не** делают проект FSD. Считай сигналы вместе:

| Сигнал | Вес |
| --- | --- |
| `steiger` / `@feature-sliced/*` / `@conarti/eslint-plugin-feature-sliced` режут граф | сильный |
| Живые слои `features` + `entities` + `shared` (часто widgets/pages) **со слайсами** и public API (`index` или принятый фасад) | сильный |
| Импорты зоны только вниз по слоям, без deep import мимо фасада | средний |
| Только папки `features/` или `shared/` без `entities`/`widgets` и без слайсов | слабый — это не FSD |
| README «мы на FSD» | слабый |
| Framework-owned `app/` / `pages/` / `routes/` | не сигнал FSD |

Решение:

- один сильный сигнал + согласованные импорты зоны → **FSD**, даже без линтера;
- слои со слайсами **и** импорты вниз, без enforcement → **FSD**;
- только слабые сигналы → не FSD; смотри feature-module / layered или спроси;
- слои есть, импорты им противоречат → смешанный: [evaluation.md](evaluation.md), затем спроси. Не мигрируй.

`src/cart/Cart.tsx` + `api.ts` без внутренних `domain/`/`application/` — **feature-module**, не Domain и не FSD.

### Layered vs Domain

Не склеивай в один трек:

| Видно | Трек |
| --- | --- |
| `pages`/`screens` + `components` + `hooks`/`services`/`store` | layered |
| `src/<name>/domain` + `application` + `ui`/`data` | domain |
| `src/<name>/` с колокацией UI+API без внутренних слоёв | feature-module |

Не заводи `application/` в layered-репо и не размазывай domain-модуль по глобальным `components/`+`services/`.

## 3. Связность, зацепление, владение

- **Связность:** в одном модуле живёт то, что меняется вместе (один пользовательский сценарий, одна сущность, один bounded context зоны). Не собирай модуль «все кнопки» или «весь Redux».
- **Зацепление:** модуль знает соседей только через их публичный контракт. Подробности — [boundaries-and-imports.md](boundaries-and-imports.md).
- **Владение:** у данных, API-метода и UI-сценария должен быть один явный владелец. Кто пишет (mutation, submit, side effect) — тот обычно и владеет сценарием; кто отдаёт справочник/чтение — тот владеет query. Детали — [state-api-and-effects.md](state-api-and-effects.md).

Не клади доменный смысл в `shared`/`common`/`utils`, «чтобы переиспользовать». Переиспользование — следствие одной ответственности, не причина свалки.

## 4. Когда выделять модуль / слайс / фичу

Выделяй **новую** границу, если выполняется хотя бы одно:

- появляется отдельный пользовательский сценарий (создать, отфильтровать, оплатить), а не ещё одно поле в той же форме;
- появляется отдельная сущность/ресурс с собственным API и UI, который уже не влезает в существующий модуль без чужих импортов;
- два потребителя тянут одну и ту же внутренность — нужен public API, а не копипаст и не deep import;
- god-module смешивает несвязанные сценарии и его нельзя править, не ломая соседей.

**Не** выделяй, если:

- это ещё один кусок того же сценария (валидация, мелкий UI, локальный хелпер) — положи внутрь существующего модуля как у аналога;
- хочется «правильную папку из учебника», а в зоне так не делают;
- дробление заставит два слайса импортировать друг друга по кругу.

Спорно — открой аналог той же зоны и повтори **его** зерно, не теоретический минимум/максимум.

## 5. Смешанный или неизвестный проект

Порядок, без миграции репозитория:

1. Определи стиль **зоны изменения** (соседние папки и импорты), не «всего src».
2. Клади новое как в этой зоне.
3. Два равноправных стиля в одной зоне или сигналов мало — **спроси**, в каком стиле вести это место. Сверка кейсов — [evaluation.md](evaluation.md).
4. Не создавай второй архитектурный стиль рядом со старым (FSD-слои посреди feature-folders, `entities/` «для одной новой фичи», `application/` в layered-репо).
5. Не мигрируй проект на FSD (и ни на какой другой шаблон) без явного запроса.
6. Legacy не выравнивай «заодно». Перенос — [refactoring.md](refactoring.md): сохрани публичный контракт, двигай только затронутое.

Fallback скила: неизвестно → спроси → копируй соседей зоны. Не угадывай канон.
