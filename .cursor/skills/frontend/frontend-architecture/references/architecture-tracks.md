# Архитектурные треки

Читай **только свой раздел** после шага 2 в `SKILL.md`. Преамбулу — всегда. Другие треки не применяй «на всякий случай» и не смешивай правила слоёв.

Ни один трек не лучше остальных универсально. Выбирает репозиторий (дерево + импорты + enforcement), не привычка модели.

| Трек | Когда | Раздел |
| --- | --- | --- |
| FSD | Живые слои `features`+`entities`+`shared` (часто ещё widgets/pages) со слайсами и импортами вниз. Enforcement усиливает, не обязателен | [FSD](#fsd) |
| Feature / module | Вертикальные фичи/модули без FSD-слоёв и без внутренних `domain/`+`application/` | [Feature / module](#feature--module) |
| Layered | Технические папки: screens/pages + components + hooks/services/store | [Layered](#layered) |
| Domain | Вертикальный модуль домена с внутренними слоями `domain` / `application` / `ui` / `data` | [Domain](#domain) |

Смешанный / неясный — сначала [principles-and-discovery.md](principles-and-discovery.md), сверка [evaluation.md](evaluation.md), затем спроси. Не читай все разделы треков подряд. Layered и Domain — **разные** треки: не смешивай их правила.

Public API, циклы, deep import — [boundaries-and-imports.md](boundaries-and-imports.md). State/API — [state-api-and-effects.md](state-api-and-effects.md).

## FSD

Читай, только если выбран трек FSD.

Типичные слои (верх зависит от низа, не наоборот):

```
app → pages → widgets → features → entities → shared
```

- **app** — composition root продукта: провайдеры, роутер приложения, входные стили. Не путай с `app/` Next/Nuxt/Remix (см. [principles-and-discovery.md](principles-and-discovery.md)).
- **pages** — сборка экрана из widgets/features/entities, маршрутный слайс.
- **widgets** — крупные самодостаточные блоки экрана (шапка, таблица со обвязкой), композиция features/entities.
- **features** — пользовательский сценарий (создать, фильтровать, войти).
- **entities** — бизнес-сущность: тип, карточка, селект сущности. Query чтения сущности — **эвристика**, только если так уже делают аналоги зоны. Не внедряй сплит query/mutation «из учебника».
- **shared** — инфраструктура без доменного смысла: UI-кит, конфиг, либы, API-клиент-база.

Слой **`processes/` не обязателен**. Если его нет в репо — **не создавай**. Если есть — положи туда только то, что уже кладут в `processes/` соседи (обычно многошаговые процессы между pages и features). Не восстанавливай «полный канон FSD 2.0» ради отсутствующего слоя.

Сегменты слайса бери у **аналога**, не полный учебный набор. Часто встречаются `ui`, `model`, `api`, `lib` — заводи только те, что в этой зоне уже есть. Не добавляй `config` / `processes` сегмент, если соседи без них живут.

Слайсы: один слайс = одна сущность или один сценарий. Группировка — как в репо: плоский `features/createSkill` или вложенный `features/skill/createSkill`. Не перекладывай чужой канон вложенности.

```
entities/<slice>/
  index.ts          ← public API слайса
  ui/
  model/
  api/
```

Потребители импортируют public API слайса (`@/entities/<slice>` или относительный `index`), не файл внутри `ui/` / `api/`. Кросс-импорт сущностей — только если в репо уже есть принятый канал (`@x` или аналог); не выдумывай `@x` в проекте без него. Подробности — [boundaries-and-imports.md](boundaries-and-imports.md).

**Не делай на этом треке:**

- не импортируй верхний слой из нижнего (`entities` ↛ `features`);
- не клади доменный UI и сценарии в `shared`;
- не превращай page в богатую реализацию таблицы/формы, если в репо page уже только композирует;
- не заводи второй стиль (`src/modules/` рядом) «для новой фичи».

Канон конкретного FSD-репозитория (имена сегментов, query vs mutation, исключения steiger) — только из **этого** репо, не из учебника и не из примеров скила. Этот раздел — не «идеальный FSD».

## Feature / module

Читай, только если выбран трек feature/module.

Основные папки — вертикальные фичи или модули, без обязательных FSD-слоёв:

```
src/features/auth/
src/features/cart/
src/modules/billing/
src/auth/
```

Внутри фичи обычно колокация: UI, хуки, API, локальный стейт рядом. Имена внутренних папок — как у соседей (`components`, `hooks`, `api`, `model`), не навязывай FSD-сегменты `ui`/`model`/`api`, если в репо другие.

Страницы/роуты **собирают** фичи. Общий код без фиче-смысла — `shared` / `lib` / `ui` **этого** репо, не свалка доменных кнопок.

Граница фичи:

- снаружи — public API фичи (`index.ts`, пакет экспортов или то, что импортируют соседи);
- фича A не лезет во внутренности фичи B;
- общее между фичами — вниз в shared или в явный контракт, не навстречу друг другу.

```
features/cart/
  index.ts
  CartPage.tsx          ← или pages/ композирует Cart
  api.ts
  useCart.ts
```

**Не делай на этом треке:**

- не создавай слои `entities/` / `widgets/` / FSD-`app/`, чтобы «было правильнее»;
- не размазывай одну фичу по техническим папкам репо (`components/Cart*`, `hooks/useCart`, `services/cart`), если соседи держат фичу целиком;
- не тащи query/mutation сущности в глобальный `services/`, если у фич API лежит внутри фичи.

Nx / `eslint-plugin-boundaries` с тегами фич — соблюдай теги репо, не FSD-иерархию.

## Layered

Читай, только если выбран трек layered (технические слои). Не применяй правила Domain.

```
pages/ или screens/   →  components/  →  hooks/  →  services/ | store/ | api/
utils/ / lib/ — без знания верхних слоёв
```

UI не ходит в сеть напрямую, если соседи уже прячут это в services/api. `utils` не импортирует компоненты и страницы.

Доменные карточки и формы живут в `components/` (или как у соседа), API — в `services/`/`api/`/`hooks/`. Страница — wiring, не место всех правил, если соседи уже вынесли их вниз.

**Не делай на этом треке:**

- не заводи `src/<domain>/domain` + `application` + `data` — это трек Domain, второй стиль;
- не наклеивай FSD-имена (`entities`, `features`, `widgets`) на технические папки;
- не вынимай query в несуществующий слой entities;
- не создавай `shared` как третий стиль; общий код — как у соседей (`lib`, `utils`, `kit`).

Направление: экран → компоненты/хуки → сервисы. Обратно нельзя.

## Domain

Читай, только если выбран трек domain. Не применяй правила Layered.

Признак: вертикальный модуль **с внутренними слоями**, не просто папка `src/cart/` с колокацией (это feature-module).

```
src/<domain>/
  domain/ или model/      ← сущности, правила, типы
  application/            ← сценарии, use-cases
  ui/ или presentation/
  data/ | infrastructure/ ← API, адаптеры
```

Зависимости **внутрь / к домену**: UI и инфраструктура зависят от домена, домен не знает страницы и HTTP-клиент. Порты/адаптеры — только если в репо они уже есть; не внедряй гексагональную обвязку в простой layered-проект (`components/` + `services/`).

Страница/container — композиция и wiring. Модуль не импортирует роуты и соседние домены вглубь: только их публичный фасад.

**Не делай на этом треке:**

- не размазывай домен по глобальным `components/` + `services/`, если модуль уже вертикальный;
- не наклеивай FSD-имена слоёв (`entities`, `features`, `widgets`);
- не поднимай доменные правила на страницу «чтобы быстрее»;
- не создавай `shared` как третий стиль; общий код — как у соседей (`lib`, `platform`, `kit`).

Направление импортов и циклы — [boundaries-and-imports.md](boundaries-and-imports.md). Перенос legacy — [refactoring.md](refactoring.md).
